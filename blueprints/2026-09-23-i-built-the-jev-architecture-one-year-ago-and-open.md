# "Jev 아키텍처"를 1년 먼저 오픈소스로 구현한 프로젝트로 대체 파이프라인 구축하기

## 개요
Reddit/HN에 공개된 이 프로젝트는 Jev(TypeSafe AI System One)가 출시되기 약 1년 전에 동일한 발상 — 텍스트 생성 대신 타입 값과 확신도를 즉시 반환하는 경량 추론 아키텍처 — 를 독립적으로 구현해 오픈소스로 공개한 것이다. Jev API 키가 대기열제라 접근이 불확실한 상황에서, 이 오픈소스 구현을 로컬에서 직접 돌려 "Jev와 동일한 인터페이스(noul/choice/score류 타입 반환)"를 가진 분류·라우팅 파이프라인을 지금 당장 macOS에서 구축할 수 있다는 점이 핵심 가치다. 이를 통해 Jev 키 발급을 기다리지 않고도 동일한 상품(이메일/티켓 분류, 저비용 라우팅 SaaS)을 먼저 만들어 검증하거나, 향후 Jev로 손쉽게 교체 가능한 추상 계층을 미리 짜둘 수 있다.

## 구현 가능성 — 중
- 오픈소스 코드가 실제로 공개되어 있고 별점/댓글 수(HN 22포인트, 댓글 1개)로 미루어 초기 단계 프로젝트라 문서화 수준이나 유지보수 상태가 검증되지 않았음 — 코드를 직접 읽고 이해하는 데 시간이 필요함.
- 아키텍처 자체(텍스트 대신 타입+확신도 반환)는 결국 "분류기 + 캘리브레이션된 확신도" 문제로 환원되므로, 로컬 임베딩 모델이나 소형 파인튜닝 분류기로 재구현 가능한 구조라 기술적 난이도는 감당 가능한 수준.
- 다만 Jev의 실제 API와 100% 호환되는 인터페이스인지는 원문만으로 확인 불가하며, 리포지토리 상태(스타 수, 최근 커밋, 라이선스)를 먼저 확인해야 착수 여부를 확정할 수 있어 "상"이 아닌 "중"으로 평가.

## 필요 도구
- 해당 오픈소스 리포지토리 (원문 링크 기준 Reddit 게시자가 언급한 GitHub 저장소 — 무료, 라이선스 확인 필요)
- Python 3.11+ (무료, 로컬 실행 환경)
- Hugging Face `transformers` / `sentence-transformers` (무료, 로컬 임베딩·분류기 대체 구현 시)
- Ollama 또는 llama.cpp (무료, 로컬 소형 LLM 백엔드로 아키텍처 재현 시)
- `llm` CLI + `llm-typesafe` 플러그인 (무료, 오픈소스 — Jev 키 발급 후 동일 인터페이스로 교체할 때 사용)
- SQLite (무료, 분류 결과 및 확신도 로그 저장)
- Docker Desktop (무료 개인용, 로컬 격리 실행 환경)
- GitHub CLI `gh` (무료, 리포지토리 클론·이슈 확인용)
- TypeSafe AI Jev API 키 (유료, 대기열 — 추후 교체용으로만 필요, 초기 구현엔 불필요)

## 구현 단계
1. 원문의 Reddit/HN 스레드에서 실제 GitHub 저장소 링크를 확보하고, `gh repo clone`으로 로컬에 내려받은 뒤 README·라이선스·최근 커밋 이력을 확인해 유지보수 상태와 상업적 재사용 가능 여부(MIT/Apache 등)를 판단한다.
2. 저장소의 핵심 모듈(타입 스키마 정의부, 확신도 계산 로직, 추론 백엔드 연결부)을 읽고, 이것이 실제로 "텍스트 생성 없이 타입 값+확신도"를 반환하는지, 아니면 LLM 출력 후처리 파싱에 가까운지 구조를 파악한다.
3. macOS에 Python 가상환경을 만들고 저장소의 예제 스크립트를 그대로 실행해, noul(예/아니오)·choice(다중분류)·score(점수) 같은 출력 타입이 실제로 잘 동작하는지, 지연시간이 어느 정도인지 벤치마크한다(간단한 100개 샘플 문장으로 처리 시간 측정).
4. 자신의 실사용 데이터(예: Gmail CS 라벨, GitHub 이슈, Notion 인박스 항목) 50~100건을 뽑아 이 오픈소스 파이프라인에 통과시키고, 결과를 SQLite에 저장하며 사람이 직접 라벨링한 정답과 비교해 정확도·확신도 캘리브레이션 품질을 검증한다.
5. Jev API 인터페이스(입력/출력 스키마)를 인터페이스 레이어로 추상화한 얇은 래퍼 클래스를 작성해, 지금은 오픈소스 백엔드를 쓰지만 나중에 `llm-typesafe`로 백엔드만 교체 가능하도록 설계한다.
6. 검증된 파이프라인을 launchd 주기 작업으로 등록해 실사용 데이터 스트림(이메일/이슈/티켓)에 상시 적용하고, 확신도 낮은 항목은 별도 검토 큐로 분리한다.
7. 정확도와 처리 비용(로컬 실행이므로 API 비용 0원)을 수치화한 뒤, "Jev API 대기 중인 팀을 위한 임시 대체 파이프라인 셋업 대행" 또는 "로컬 우선 저비용 분류 자동화 컨설팅" 형태로 소규모 유료 파일럿을 제안한다.
8. Jev API 키 발급 시 5단계의 래퍼 계층만 교체해 성능·비용을 오픈소스 버전과 비교하고, 더 나은 쪽을 프로덕션 백엔드로 채택한다.

## 예상 공수
- 1~3단계 (리포지토리 조사 및 로컬 실행 검증): 4~7시간
- 4단계 (실데이터 정확도 검증): 4~6시간
- 5~6단계 (추상화 레이어 설계 및 스케줄링): 6~9시간
- 7~8단계 (파일럿 제안 및 Jev 교체 대비): 5~10시간
- 총 19~32시간, 난이도: 중 (Python/ML 기초와 코드 리딩 능력 필요, LLM 미세조정 경험 있으면 가속)

## 리스크/유의점
- 원문 정보만으로는 정확한 리포지토리 URL, 스타 수, 최근 활동 여부를 알 수 없으므로 착수 전 반드시 실제 링크를 확인하고 프로젝트가 "장난감 수준 데모"인지 "실사용 가능한 라이브러리"인지 먼저 판별해야 함.
- 개발자 1인이 만든 초기 단계 오픈소스일 가능성이 높아 보안 취약점, 프롬프트 인젝션 방어 부재, 라이선스 조건(상업적 이용 제한 등) 위험이 있으므로 코드 감사 없이 바로 고객 데이터에 적용하지 말 것.
- "Jev 아키텍처"를 먼저 구현했다는 주장 자체가 사후적 재해석(hindsight labeling)일 수 있어, 실제 성능·확신도 캘리브레이션 품질이 Jev 공식 모델과 크게 다를 수 있음 — 반드시 자체 데이터로 정확도를 별도 검증해야 함.
- 오픈소스 백엔드로 만든 파이프라인을 유료 상품화할 경우, 저장소 라이선스가 상업적 재배포/SaaS 운영을 허용하는지 반드시 확인(GPL 계열이면 소스 공개 의무 발생 가능).
- 이메일·티켓 등 민감 데이터를 로컬 오픈소스 모델에 흘려보내는 것 자체는 외부 전송이 없어 상대적으로 안전하지만, 추후 Jev API로 전환 시에는 데이터 처리 방침을 고객에게 다시 고지해야 함.
