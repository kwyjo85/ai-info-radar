# 스펙 주도 개발(SDD)으로 Claude Code 통제하기

## 쉽게 말하면
Claude Code는 시키는 대로 뭐든 열심히 만들어주는 신입 개발자 같은데, 문제는 "뭘 만들지"를 명확히 안 정해주면 지가 알아서 엉뚱한 방향으로 완성해버린다는 것입니다. OpenSpec은 코드를 짜기 전에 "이걸 이렇게 만들 거야"라는 설계도(스펙)를 먼저 문서로 합의하고, 그 설계도를 기준으로만 코딩·검수하게 만드는 도구입니다. 집 짓기 전에 도면부터 그리고 그 도면대로 시공 감리하는 것과 같습니다.

## 이걸로 할 수 있는 것
1. ig-dashboard에 "카드별 메모/상태" 기능을 추가하기 전, 스펙 문서로 동작 방식을 먼저 못 박아두고 Claude Code에게 구현시켜서 왔다갔다 재작업을 줄인다.
2. Jev 자동화 스킬(예: 브리핑 생성, 채점 로직 수정)처럼 규칙이 복잡한 기능을 바꿀 때, 기존 스펙과 새 요구사항의 충돌을 문서 단계에서 미리 발견한다.
3. 외주·부업으로 Claude Code 기반 자동화를 팔 때, "스펙부터 합의 → 구현 → 스펙 대비 검수"라는 프로세스 자체를 상품화해 고객에게 "결과물이 원하는 대로 나온다"는 신뢰를 판매한다.

## 개요
OpenSpec은 AI 코딩 어시스턴트가 코드를 작성하기 전에 요구사항을 spec 파일로 명문화하고, 구현과 리뷰를 그 spec 기준으로 진행하도록 강제하는 CLI 프레임워크입니다. "말은 잘 듣지만 방향을 자주 틀리는" AI 코딩의 근본 문제를, 대화로 계속 정정하는 대신 문서로 한 번에 합의하는 구조로 해결합니다. 실제 사용자 규모(★70k, 주간 +1,538)가 검증돼 있어 도입 리스크가 낮습니다.

## 구현 가능성 — 상
- Claude Code와의 연동이 공식 지원되며 npx로 설치하는 CLI라 진입장벽이 낮음.
- 이미 개인 프로젝트(ai-info-radar, ig-dashboard)에서 Claude Code로 기능을 반복 추가하는 워크플로우가 존재해, 곧바로 적용 가능한 실사용 맥락이 있음.
- 혼자 쓰는 프로젝트라 "팀 합의용 스펙"이라는 원래 취지와는 다르지만, "AI에게 정확히 지시하기 위한 체크리스트" 용도로는 충분히 가벼운 도입이 가능.

## 필요 도구
- **OpenSpec CLI** (`@fission-ai/openspec`, npx로 실행) — 무료, 오픈소스
- **Node.js/npm** — 무료 (이미 설치돼 있다고 가정)
- **Claude Code** — 기존 사용 중인 도구, 별도 비용 없음 (구독은 기존 유지)
- (선택) **Cursor** — 이미 안 쓰면 불필요, OpenSpec은 Claude Code만으로도 완결됨

## 구현 단계
1. ig-dashboard 또는 ai-info-radar 저장소 루트에서 `npx @fission-ai/openspec init` 실행해 스펙 폴더 구조 생성.
2. README Quick Start를 확인해 스펙 파일 템플릿(요구사항, 수용 기준 등) 형식 파악.
3. 다음에 추가할 기능 하나(예: "카드별 메모/상태" 또는 "오늘의 액션 추천")를 골라, 코딩 요청 전에 스펙 파일을 먼저 작성 — 입력/출력, 예외 상황, UI 동작을 문장으로 명시.
4. Claude Code에게 "이 스펙 파일을 기준으로 구현해줘"라고 요청하고, 구현 완료 후 스펙과 결과물을 대조 리뷰.
5. 기존 방식(스펙 없이 바로 요청)과 비교해 재작업 횟수·왔다갔다 대화 수가 줄었는지 1~2개 기능으로 체감 테스트.
6. 효과가 확인되면 "규모가 큰 변경(새 페이지, 데이터 구조 변경 등)"에만 선택적으로 스펙 작성을 습관화하고, 사소한 수정(오탈자, 스타일)은 기존처럼 바로 요청.
7. (수익화 관점) 이 프로세스가 익숙해지면, Claude Code 외주/컨설팅 시 "스펙 문서 + 구현 + 검수" 패키지로 제안서에 포함시켜 결과물 품질을 보장하는 근거로 활용.

## 예상 공수
- 초기 설치·템플릿 파악: 20~30분
- 첫 스펙 문서 작성 연습 (기능 1개): 30~40분
- 전체 습관화까지 적응 기간: 2~3회 기능 추가 사이클 (각 사이클에 스펙 작성 15~20분 추가 소요)
- 난이도: 하~중 (CLI 설치는 쉬우나, "좋은 스펙 작성" 자체는 연습이 필요한 스킬)

## 리스크/유의점
- 혼자 쓰는 프로젝트라 팀 협업용으로 설계된 스펙 프로세스가 과할 수 있음 — 작은 수정까지 스펙화하면 오히려 속도 저하.
- 스펙 작성 자체를 대충 하면 "스펙 없이 하던 것"과 차이가 없어 도입 효과 체감이 안 될 수 있음 — 처음 1~2회는 의식적으로 꼼꼼히 작성해볼 것.
- ig-dashboard/ai-info-radar처럼 이미 구조가 잡힌 소규모 프로젝트에서는 대규모 변경이 자주 없어 적용 빈도가 낮을 수 있음 — "선택적 적용" 원칙을 지켜야 함.
