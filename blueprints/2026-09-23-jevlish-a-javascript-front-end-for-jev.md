# Jevlish 기반 "브라우저 네이티브 Jev 위젯" SaaS 수익화

## 개요 — 무엇을 자동화하는가, 어떤 가치가 있는가
Jevlish는 Jev(TypeSafe AI System One)를 자바스크립트에서 바로 호출할 수 있게 해주는 프런트엔드 바인딩으로, 서버 왕복 없이 브라우저/Node 환경에서 타입 값+확신도를 즉시 받아올 수 있게 해줍니다. 이를 활용해 "폼 자동완성·입력 검증·의도 분류"처럼 저지연이 중요한 UI 상호작용을 LLM API 호출 없이 처리해주는 임베드형 JS 위젯(예: 스크립트 한 줄 삽입형 SDK)을 만들어, 노코드/SMB 웹사이트 운영자에게 월 구독으로 판매할 수 있습니다. Jev가 100배 빠르고 저렴하다는 특성상 "클릭당 과금이 거의 없는 실시간 스마트 폼"이라는 차별화 포인트를 만들 수 있습니다.

## 구현 가능성 — 중
- Jevlish 자체가 이미 프런트엔드 통합 문제(타입 매핑, 비동기 호출, 브라우저 호환)를 해결해 둔 상태라 초기 통합 난이도는 낮음
- 다만 원문이 HN 포인트 2점·댓글 2개로 아직 검증이 얕은 개인 프로젝트(GitHub Pages 데모)라, 프로덕션 안정성·유지보수 지속 여부를 직접 확인해야 함
- Jev API 자체의 정식 가격 정책·SLA가 2026-09 출시 직후라 유동적이어서, 이를 전제로 한 구독형 위젯의 원가 구조가 아직 불확실
- MacBook에서 데모/PoC 제작은 하루 이내 가능하나, "SaaS로 판매 가능한 수준"까지 가려면 결제·멀티테넌시 등 추가 작업 필요

## 필요 도구
- **Jevlish** (오픈소스, https://jacobgoldfarb.github.io/Jevlish/) — 무료, MIT류 라이선스 여부 확인 필요
- **Jev API** (TypeSafe AI System One) — 유료, 호출당 과금 예상 (정식 가격표 확인 필요)
- **Vite + TypeScript** — 무료, 임베드 위젯 번들링
- **Cloudflare Workers** — 무료 티어 있음, API 키 프록시/레이트리밋 서버리스 처리
- **Stripe Billing** — 유료(수수료), 월 구독 결제
- **Clerk 또는 Auth.js** — 무료 티어, 고객사별 API 키/테넌트 관리
- **Playwright** — 무료, 임베드 스크립트 크로스브라우저 테스트

## 구현 단계
1. Jevlish 데모 페이지와 GitHub 저장소를 직접 열어 API 표면(초기화 함수, 반환 타입 스키마, 에러 처리 방식)을 문서화하고 로컬에서 `npm install`로 재현
2. 실사용 시나리오 하나를 정해 PoC 제작 — 예: 이메일 문의 폼에서 "문의 유형(환불/배송/기타) + 확신도"를 타이핑 중 실시간으로 분류해 담당 부서로 자동 라우팅하는 위젯
3. Jev API 키를 브라우저에 직접 노출하지 않도록 Cloudflare Workers로 프록시 엔드포인트 구성, 여기서 테넌트별 레이트리밋·사용량 로깅 추가
4. Vite로 `<script>` 한 줄 삽입 가능한 UMD 번들 제작, 호스트 사이트의 폼 요소를 자동 탐지해 Jev 분류 결과를 붙여주는 방식으로 설계
5. Stripe Billing으로 "무료(월 500회) / Pro(월 $19, 1만 회) / 팀(커스텀)" 3단 요금제 구성, Clerk로 고객별 API 키 발급 자동화
6. 랜딩 페이지 제작 후 Product Hunt, HN Show, 국내 노코드/SMB 커뮤니티(오픈카톡, 디스콰이엇)에 데모 GIF와 함께 공개
7. 초기 3~5개 베타 고객(개인 쇼핑몰, 문의 폼 많은 1인 서비스)에게 무료로 붙여주고 실사용 지연시간·정확도 피드백 수집 후 가격 조정

## 예상 공수
- Jevlish/Jev API 조사 및 PoC: 4~6시간
- 임베드 위젯 번들 + 프록시 서버: 8~10시간
- 결제/멀티테넌시(Stripe+Clerk) 연동: 5~6시간
- 랜딩 페이지 + 베타 배포: 3~4시간
- **총 20~26시간, 난이도: 중~상** (기술 난이도 자체는 중이나, "월 구독 SaaS"로 완성하려면 결제·인증 등 비핵심 작업 비중이 큼)

## 리스크/유의점
- Jevlish가 개인 사이드 프로젝트 수준(포인트 2점)이라 유지보수 중단·API 변경 시 의존 리스크가 큼 — 초기엔 Jevlish를 참고만 하고 자체 경량 래퍼를 직접 작성하는 것도 대안
- Jev 자체 이용약관에 "재판매/화이트라벨 SaaS로 임베드 판매" 허용 여부를 반드시 확인 필요 (API 재판매 금지 조항이 있을 수 있음)
- 브라우저에서 Jev를 직접 호출할 경우 API 키 노출 위험이 있으므로 반드시 서버 프록시를 거쳐야 하며, 클라이언트에 원본 키를 절대 심지 않도록 주의
- "확신도 낮은 분류 결과"를 사용자에게 어떻게 노출할지(예: 낮은 확신도 시 사람 검수로 폴백) 설계하지 않으면 오분류로 인한 고객 신뢰 하락 위험
