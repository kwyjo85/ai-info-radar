# Jev는 분류용, 복잡한 생각은 LLM에게

## 쉽게 말하면
지금 쓰는 자동화 스크립트 대부분은 사실 "이 메일이 스팸인가 아닌가", "이 배포가 성공했나 실패했나" 같은 단순 O/X 판단인데, 이걸 비싸고 느린 추론형 AI(Claude, GPT 등)에게 시키고 있는 경우가 많습니다. 비유하자면 동네 마트 계산대에 박사급 회계사를 앉혀놓고 잔돈 계산만 시키는 셈입니다. Jev는 이런 "빠른 직관형 판단"만 초고속·저비용으로 처리하는 전용 모델이고, 복잡한 글쓰기·기획·코드 작성은 그대로 LLM이 맡는 역할 분담 구조를 만드는 것이 이번 아이디어의 핵심입니다.

## 이걸로 할 수 있는 것
1. 매일 자동으로 돌아가는 ai-info-radar 수집 파이프라인에서 "이 기사가 관심 주제와 관련 있는가"를 Jev로 1차 필터링해 Claude 호출 비용과 시간을 줄인다.
2. 인스타 대시보드나 메일함에 쌓이는 항목을 "긴급/일반", "확인 필요/무시" 같은 라벨로 Jev가 즉시 분류하게 해 매일 하던 수동 트리아지 작업을 없앤다.
3. Claude Code 에이전트가 만든 코드나 블루프린트 출력이 규칙(형식, 금칙어, 스키마)을 지켰는지 Jev로 빠르게 검증하는 "저비용 게이트키퍼"를 만들어 컨설팅 납품 파이프라인에 끼워 판다.

## 개요
소프트웨어의 의사결정 지점 중 "예/아니오", "카테고리 A/B/C 중 선택", "0~1 점수" 같은 System 1형 판단을 골라내 Jev로 대체하고, 실제 서술·추론이 필요한 부분만 Claude/GPT 같은 System 2 모델에 남기는 하이브리드 파이프라인을 만드는 작업입니다. 가치는 (1) 추론 모델을 분류에 낭비하던 지연·토큰 비용 절감, (2) 파이프라인 처리량 증가로 더 많은 자동화를 같은 예산에 태울 수 있다는 점, (3) 이 "분류-추론 분리 패턴" 자체를 컨설팅 상품(비용 절감 진단·구현)으로 재판매할 수 있다는 점입니다.

## 구현 가능성: 상
- ai-info-radar에 이미 매일 도는 수집·분류 파이프라인이 있어 Jev를 끼워 넣을 지점이 명확함(기사 관련성 판단, 채점 필드 일부).
- Jev는 API 호출 방식이 단순(타입 값 + 확신도 반환)이라 통합 코드량이 적고, 기존 LLM 호출부를 조건 분기로 대체하는 정도의 작업.
- 다만 Jev는 2026-09 출시라 실제 API 스펙·요금·엔드포인트 세부사항은 공식 블로그·문서를 직접 확인해야 하는 부분이 있어 "상"이되 첫 단계에 리서치가 필요함.

## 필요 도구
- **Jev API** (TypeSafe AI, 유료·종량제 추정 — early access 요금 정책 직접 확인 필요), 환경변수 `TYPESAFE_API_KEY`
- **Claude Code** (기존 사용 중, 파이프라인 코드 수정·통합 자동화에 활용, 무료 사용분 내)
- **Sam Witteveen 예제 코드 저장소**: https://github.com/samwit/llm-tutorials (무료, Choice/Score/Noul 데모 패턴 참고)
- **ai-info-radar 기존 수집 스크립트** (프로젝트 내부, 관련성 판단·채점 로직이 있는 파일)
- **간단한 비용/지연 로깅 도구** (예: Python `time` + 호출 로그 CSV, 무료) — Jev 도입 전후 비교용

## 구현 단계
1. 영상(16분)과 typesafe.ai 블로그를 보며 Jev의 3가지 호출 패턴(Choice/Score/Noul)과 실제 요청/응답 형식을 확인한다.
2. github.com/samwit/llm-tutorials의 예제 코드를 로컬에서 그대로 실행해 API 키 설정과 응답 구조를 직접 눈으로 확인한다.
3. ai-info-radar 파이프라인 코드를 열어 "한 단어/한 라벨 답이면 되는 결정" 지점을 목록화한다 (예: 기사-주제 관련성 판단, 중복 기사 여부, 채점 필드 중 이진 판단 항목).
4. 그중 호출 빈도가 가장 높은 지점 1개(관련성 판단 추정)를 골라 기존 LLM 호출 코드를 Jev Choice 호출로 교체하는 브랜치를 만든다.
5. 같은 입력 100건 정도를 기존 LLM과 Jev 양쪽에 돌려 지연 시간·비용·판단 일치율을 CSV로 기록해 비교한다.
6. 일치율이 허용 범위(예: 90% 이상)면 해당 지점을 Jev로 완전히 교체하고, 나머지 서술형 판단은 그대로 Claude에 남긴다.
7. 효과가 확인되면 같은 패턴(분류는 Jev, 추론은 LLM)을 다른 자동화(메일 트리아지, 배포 실패 판단 등)에도 순차 적용하고, 이 사례를 컨설팅용 케이스 스터디로 정리한다.

## 예상 공수
- 영상 시청 + 예제 실행: 1시간
- 결정 지점 목록화 + 후보 선정: 1시간
- 코드 교체 + 통합: 2~3시간
- 비교 평가(지연·비용·정확도): 2시간
- 총합: 약 6~7시간, 난이도 하~중 (API 통합 자체는 쉽지만 early access 문서 부족으로 시행착오 가능)

## 리스크/유의점
- Jev는 2026-09 출시로 모델 지식 컷오프 이후 정보라 요금제·율제한(rate limit)·안정성이 검증되지 않았을 수 있어, 매출에 직결된 파이프라인 핵심 경로에 바로 투입하기보다 비핵심 지점부터 시범 적용할 것.
- "분류"와 "추론"의 경계가 모호한 판단(예: 애매한 관련성 판정)을 Jev에 맡기면 정확도가 떨어질 수 있으므로, 반드시 일치율 검증 후 적용 범위를 제한할 것.
- 외부 API 의존이 하나 더 늘어나는 것이므로, Jev 장애 시 기존 LLM 호출로 자동 폴백하는 경로를 남겨둘 것.
