# Quiet-Guardrails: Claude Code 수동 모드 커스터마이징

## 쉽게 말하면
Claude Code가 파일을 고치거나 명령을 실행할 때마다 "이거 해도 될까요?"라고 매번 물어보면 자동화 작업 흐름이 뚝뚝 끊깁니다. Quiet-Guardrails는 이 "물어보기"를 줄이되, 위험한 행동(파일 삭제, 강제 푸시 같은 것)만은 확실히 막아주는 안전벨트를 미리 깔아두는 도구입니다. 비유하자면 신입 직원에게 모든 결재를 다 올리라고 하는 대신, "이 정도는 알아서 해, 대신 이 몇 가지는 반드시 나한테 물어봐"라고 규칙을 정해주는 것과 같습니다.

## 이걸로 할 수 있는 것
1. Jev로 클라이언트 리포트를 자동 생성·정리하는 야간 배치 작업을 Claude Code에 맡겨두고, 위험한 명령(파일 대량 삭제 등)만 승인받도록 설정해 자는 동안 안전하게 돌린다.
2. 반복적인 코드 리뷰·리팩터링 외주 작업을 처리할 때, 매번 "이 파일 수정해도 됩니까"를 묻지 않도록 해서 처리 건당 걸리는 시간을 줄이고 더 많은 외주를 받는다.
3. 여러 클라이언트 프로젝트를 동시에 자동화 파이프라인으로 돌릴 때, 프로젝트별로 다른 가드레일(예: A사는 git push 금지, B사는 DB 접근 금지)을 설정해 실수로 인한 사고를 예방한다.

## 개요
이 리포지토리는 Claude Code의 권한(permission) 시스템 위에 커스텀 훅(hook)과 설정을 얹어, "자동 승인해도 되는 행동"과 "반드시 사람이 확인해야 하는 행동"을 세밀하게 구분해줍니다. 이를 통해 Claude Code를 더 자율적으로("headless"에 가깝게) 돌리면서도 치명적 실수(강제 푸시, 파일 삭제, 시크릿 노출 등)를 방지할 수 있어, 자동화 업무의 처리량을 늘리는 동시에 사고 리스크를 낮추는 가치가 있습니다.

## 구현 가능성
**상** — 근거: settings.json 기반 permission/hooks 설정은 Claude Code 공식 기능이라 별도 인프라 없이 macOS에서 바로 적용 가능하며, 사용자는 이미 `update-config` 스킬로 이런 설정을 다뤄본 경험(허용 목록, 훅 구성)이 있어 학습 곡선이 낮음. GitHub 코드를 그대로 클론해 자신의 `.claude/settings.json`에 병합하면 되는 수준.

## 필요 도구
- **Claude Code** (이미 사용 중, 무료/구독 요금제 내 포함)
- **GitHub CLI (`gh`)** — 리포지토리 클론용, 무료
- **quiet-guardrails 리포지토리** (`github.com/SeanMcMillan/quiet-guardrails`) — 무료, 오픈소스
- **jq** — settings.json 병합/검증용 셸 유틸, 무료
- (선택) **shellcheck** — 커스텀 훅 스크립트 검증, 무료

## 구현 단계
1. `gh repo clone SeanMcMillan/quiet-guardrails ~/tools/quiet-guardrails`로 리포지토리를 로컬에 받는다.
2. README와 `hooks/`, `settings*.json` 파일을 읽고, 이 프로젝트가 제공하는 permission 규칙(자동 승인 패턴, 차단 패턴)의 구조를 파악한다.
3. 자신의 실제 작업 프로젝트(예: `ai-info-radar`, 클라이언트 리포)에서 반복적으로 승인 프롬프트가 뜨는 명령어 유형을 1주일 정도 기록해, "자주 쓰는데 안전한 것" 목록을 뽑는다 (`fewer-permission-prompts` 스킬로 트랜스크립트 스캔해도 됨).
4. quiet-guardrails의 훅/설정을 참고해 `~/.claude/settings.json`(전역) 또는 프로젝트별 `.claude/settings.json`에 "자동 허용" 목록과 "항상 확인" 목록(git push --force, rm -rf, DB 마이그레이션 등)을 나눠 작성한다.
5. 클라이언트/프로젝트별로 리스크 수준이 다르면 프로젝트 로컬 `.claude/settings.local.json`으로 오버라이드해 세분화한다.
6. 실제 자동화 작업(Jev 배치, 외주 리뷰 등) 한 건에 적용해 하루 동안 시범 운영하고, 오탐(과도한 자동 승인)이나 누락(위험한데 안 걸림)이 없는지 점검한다.
7. 문제 없으면 dotfiles 저장소나 개인 템플릿에 이 설정을 커밋해 새 프로젝트마다 재사용한다.

## 예상 공수
- 클론·구조 파악: 30분
- 자신의 패턴 분석 및 목록 작성: 1~2시간
- 설정 병합·테스트: 1~2시간
- 총 3~5시간, **난이도: 하~중** (settings.json 문법과 셸 스크립트 이해만 있으면 됨)

## 리스크/유의점
- "조용히" 자동 승인되는 항목이 너무 넓으면 클라이언트 프로젝트에서 의도치 않은 파일 수정/삭제가 조용히 실행될 수 있음 — 처음엔 보수적으로 시작해 점진적으로 허용 범위를 넓힐 것.
- 오픈소스 개인 프로젝트라 유지보수가 중단될 수 있으므로, 훅 스크립트 내용을 직접 검토하고 필요한 부분만 발췌해 쓰는 게 안전함.
- 여러 클라이언트 프로젝트에 동일 설정을 복사할 때 시크릿/자격증명 관련 규칙이 프로젝트별로 다를 수 있음을 감안해 반드시 프로젝트별로 재검토.
