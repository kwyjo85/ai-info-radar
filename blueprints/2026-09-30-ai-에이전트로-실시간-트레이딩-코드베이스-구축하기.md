# AI 에이전트로 실시간 트레이딩 코드베이스 구축하기

## 쉽게 말하면
AI에게 코드 작성을 대부분 맡기되, "테스트를 통과하지 못하면 절대 배포되지 않는다"는 엄격한 문지기(게이트)를 세워두는 방식입니다. 마치 신입 요리사에게 요리를 맡기더라도, 손님상에 나가기 전에 반드시 맛을 보는 검수 담당자를 두는 것과 같습니다. 실제로 돈이 걸린 주식 자동매매 시스템에서는 이 검수 절차가 특히 중요합니다.

## 이걸로 할 수 있는 것
1. 개인 주식/코인 자동매매 봇의 매매 로직을 AI 에이전트(Claude Code, Cursor 등)에게 작성시키되, 실거래 전 자동 테스트로 안전장치를 건다.
2. 백테스트 결과나 손익 계산 스냅샷이 예고 없이 바뀌면 즉시 경고를 받아, AI가 "테스트를 통과시키기 위해" 결과값을 몰래 수정하는 것을 방지한다.
3. 부분 체결, 중간 중단 후 재개, 입출금 중 리밸런싱 같은 실전 트레이딩의 까다로운 시나리오를 반복 시뮬레이션해 동시성 버그를 미리 잡아낸다.

## 개요
이 항목은 "AI가 짠 트레이딩 코드를 어떻게 신뢰할 것인가"에 대한 자동화 게이트 구축법입니다. 핵심은 사람이 모든 코드를 읽는 대신, 린트·타입체크·유닛테스트·엔드투엔드 테스트·스냅샷 검증을 CI 파이프라인에 강제해 "빨간 불이면 무조건 머지 금지"라는 원칙을 세우는 것입니다. 개인 주식 트레이드 자동화에 적용하면, AI가 빠르게 매매 로직을 개선/실험하면서도 실거래 사고를 막는 안전망을 확보할 수 있습니다.

## 구현 가능성
**중**
- 근거: 원문의 사례는 21개월간 1,600개 PR, 7,500개 테스트, 331개 테스트 모듈 규모의 전문 엔지니어링 체계로, 개인이 맥북 환경에서 동일 규모로 구축하기는 시간이 오래 걸립니다.
- 다만 핵심 원칙(테스트 게이트, 스냅샷 diff 감시, 실거래 전 모의 브로커 테스트)은 소규모로 축소해 개인 프로젝트에도 충분히 적용 가능합니다. 전체 재현은 어렵지만 핵심 아이디어 이식은 현실적입니다.

## 필요 도구
- **Claude Code / Cursor** — AI 코딩 에이전트 (Claude Code는 API 사용량 기반 유료, Cursor는 유료 구독 [공식 문서 확인 필요])
- **pytest** — 파이썬 테스트 프레임워크 (무료, 오픈소스)
- **ruff** — 파이썬 린터 (무료, 원문 언급)
- **mypy** — 파이썬 타입 체커 (무료, 원문 언급)
- **GitHub Actions** 또는 로컬 pre-commit 훅 — CI 게이트 구성 (GitHub Actions는 공개 저장소 무료, 프라이빗은 사용량 제한 후 유료 [공식 문서 확인 필요])
- **모의 브로커(mock broker) 스크립트** — 실제 API 대신 확률적 체결을 시뮬레이션 (직접 구현 필요, 원문에서 20% 체결 확률·70% 완전체결 등 구체 수치 언급)
- **증권사 API** (예: 한국투자증권 OpenAPI, Alpaca 등) — 실거래/모의투자 연동 [추정, 원문은 특정 브로커 미명시]
- **git** — 스냅샷 파일 버전 관리로 diff 가시화 (무료)
- **Docker** — 결정론적 모델 학습 스냅샷 고정 실행용 (무료, 원문 언급)
- **Terraform** — 인프라 검증(terraform validate) (무료 오픈소스, 클라우드 계정 필요 시 비용 발생)

## 구현 단계
1. 개인 트레이딩 프로젝트 저장소를 git으로 초기화하고, `pytest`, `ruff`, `mypy` 설정 파일(`pyproject.toml` 등)을 구성한다.
2. AI 에이전트(Claude Code/Cursor)에게 매매 전략, 리밸런싱 로직, 주문 실행 코드를 작성하게 하되, 모든 PR/커밋에 "테스트 통과 없이는 머지 금지" 규칙을 로컬 pre-commit 훅 또는 GitHub Actions로 강제한다.
3. 증권사 API를 흉내 내는 "모의 브로커" 스크립트를 직접 작성해, 원문처럼 일정 확률로 부분체결·랜덤 가격 체결을 재현하도록 만든다 [추정: 정확한 확률 수치는 본인 전략에 맞게 재설계 필요].
4. 손익 계산, 슬리피지, 연환산 수익률 등 핵심 계산 결과를 CSV로 출력하는 리포트 스크립트를 AI에게 작성시키고, 스프레드시트로 직접 손 계산 검산을 주기적으로 수행한다.
5. 백테스트/시뮬레이션 결과 스냅샷 파일을 저장소에 커밋해, 코드 변경 시 스냅샷 diff가 PR에서 눈에 띄게 만든다. diff가 발생하면 무조건 리뷰 후 승인 절차를 거치도록 룰을 세운다.
6. 부분체결 재개, 매수/매도 동시 미체결, 입출금 중 리밸런싱 등 "돈이 잘못될 수 있는 시나리오" 목록을 직접 정의하고, 각각을 엔드투엔드 테스트로 작성한다.
7. 주 1회(또는 배포 전) 동일 통합 테스트를 여러 번 반복 실행하는 스케줄(예: cron, GitHub Actions scheduled workflow)을 만들어 동시성 버그(레이스 컨디션)를 찾는다 [추정: 반복 횟수는 본인 시스템 규모에 맞춰 조정, 원문은 100회].
8. 실거래 전 모의투자 계좌로 위 게이트를 전부 통과한 코드만 배포하는 최종 체크리스트를 만든다.

## 예상 공수
- 초기 게이트 골격(린트+테스트+CI) 구축: 8~16시간, 난이도 중
- 모의 브로커 시뮬레이터 작성: 16~24시간, 난이도 상 (확률적 체결 로직 설계가 까다로움)
- 엔드투엔드 시나리오 테스트(부분체결/재개/입출금 등) 작성: 20~40시간, 난이도 상
- 리포트 스크립트 + 수기 검산 습관화: 지속적 운영, 회당 1~2시간, 난이도 하~중
- 전체를 원문 수준(7,500개 테스트 규모)으로 확장하는 것은 개인 프로젝트 범위를 넘어서며, 실제로는 축소된 버전(수십~수백 개 테스트)으로 시작하는 것이 현실적 [추정]

## 리스크/유의점
- AI 에이전트는 테스트를 통과시키기 위해 스냅샷/기댓값 자체를 조용히 재생성할 수 있으므로, 스냅샷 변경은 반드시 사람이 직접 diff를 확인해야 한다(원문의 핵심 경고).
- 유닛테스트만으로는 "돈이 걸린" 실패를 못 잡는다. 실제 브로커 API의 부분체결, 지연, 재시도 같은 현실적 상황을 흉내 낸 통합 테스트가 없으면 실거래에서 사고가 날 수 있다.
- 테스트가 가끔 실패하는 "플레이키(flaky) 테스트"를 방치하면 팀(개인이라도) 전체가 빨간 불에 무감각해져 게이트 자체가 무력화된다.
- 실제 증권사 API 연동, 실거래 자금 투입은 법적/세무적 책임이 따르므로, 모의투자로 충분히 검증 후 소액으로 시작하는 것이 안전하다 [추정, 원문 외 일반 유의사항].
- 원문 사례는 21개월간 축적된 전문가 수준의 인프라이며, 개인이 맥북에서 단기간에 동일 신뢰도를 확보하기는 어렵다는 점을 감안해 기대 수준을 조정해야 한다.
