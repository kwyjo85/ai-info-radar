# Jev-rs: Rust 기반 LLM→Jev 서버 변환 도구 도입 블루프린트

## 쉽게 말하면
Jev-rs는 일반 LLM(느리고 비싼 "말하는 AI")을 Jev("즉답형 판단 AI") 방식의 서버로 바꿔주는 Rust 도구입니다. 비유하자면, 매번 긴 설명을 늘어놓는 상담원 대신, 미리 정해진 답안지 중 하나를 초고속으로 찍어주는 자동응답기로 개조하는 것과 비슷합니다. 이렇게 하면 반복적이고 정형화된 판단 작업을 훨씬 빠르고 싸게 처리할 수 있습니다.

## 이걸로 할 수 있는 것
1. Claude Code로 자동화 파이프라인을 만들 때, 단순 분류·라우팅 판단(예: "이 이슈는 버그냐 기능요청이냐")을 LLM 호출 대신 Jev 서버로 돌려 API 비용을 대폭 절감한다.
2. AI 정보 레이더(ai-info-radar) 같은 반복 실행 배치 작업에서, 기사 필터링·점수 매기기 같은 저복잡도 판단 단계를 Jev-rs로 대체해 launchd 스케줄 작업의 API 비용과 대기 시간을 줄인다.
3. 고객에게 판매할 자동화 상품(예: 이메일 분류기, 리드 스코어링 봇)의 원가를 낮춰 마진을 높이거나, "초고속 판단 엔진 탑재"를 세일즈 포인트로 내세운다.

## 개요
Jev-rs는 기존 LLM(로컬 모델 또는 API 기반)을 Jev 프로토콜을 따르는 서버로 감싸, 텍스트 생성 대신 미리 정의된 타입 값+확신도를 즉시 반환하도록 변환합니다. 자유 서술이 필요 없는 분류/라우팅/판정 작업에서 지연시간과 토큰 비용을 크게 줄이는 것이 핵심 가치이며, Claude Code 워크플로우나 배치 자동화의 "저부가가치 반복 판단" 구간을 값싼 하위 계층으로 내려보내는 데 쓸 수 있습니다.

## 구현 가능성: 하
근거:
- GitHub 스타/포인트가 매우 낮고(HN 포인트 2점, 댓글 1개) 문서·커뮤니티 검증이 사실상 없는 초기 프로젝트로, 프로덕션 신뢰도가 낮습니다.
- Jev/TypeSafe AI 자체가 2026-09-15 출시된 지 2주밖에 안 된 신생 서비스이며, `TYPESAFE_API_KEY` 발급·요금제·SLA 등 실무 정보가 부족합니다.
- Rust 빌드 체인(cargo, 의존 크레이트, 실제 Jev 프로토콜 스펙 이해)이 필요해 개인 MacBook에서 바로 "복붙 실행" 수준이 아닙니다.
- 다만 개념 검증(PoC) 목적이라면 소규모 실험은 상 수준으로 쉽게 가능합니다.

## 필요 도구
- Rust 툴체인: `rustup`, `cargo` (무료)
- jev-rs 소스코드: `git clone https://github.com/yijunyu/jev-rs` (무료, 단 문서 부족)
- TypeSafe AI 계정 및 API 키 `TYPESAFE_API_KEY` (요금제 미확인 — 유료 가능성 높음, 확인 필요)
- 변환 대상 LLM: 로컬 모델(예: Ollama로 구동하는 소형 모델) 또는 기존 API 키(Claude API 등) — 로컬이면 무료, API면 종량 과금
- 테스트용 HTTP 클라이언트: `curl` 또는 Postman (무료)
- (선택) Docker — 서버 격리 실행용 (무료)

## 구현 단계
1. `git clone https://github.com/yijunyu/jev-rs` 후 README와 소스코드를 직접 읽어 프로토콜 스펙(입출력 타입, 인증 방식)을 파악한다 — 문서가 부실하므로 코드 리딩이 필수.
2. `rustup`으로 Rust 최신 안정 버전 설치 확인 후 `cargo build`로 로컬 빌드가 성공하는지 먼저 검증한다.
3. TypeSafe AI 사이트(typesafe.ai)에서 API 키 발급 절차와 요금 정책을 확인하고, 무료 티어가 있는지부터 확인한다 — 없으면 이 단계에서 도입 여부를 재검토.
4. 변환 대상 LLM을 하나 정한다(비용 절감이 목적이므로 처음엔 로컬 소형 모델이나 저가 API 모델로 PoC).
5. jev-rs로 해당 LLM을 감싸 로컬 서버로 띄우고, `curl`로 간단한 분류 요청(예: "이 텍스트는 긍정/부정?")을 보내 응답 지연시간과 정확도를 LLM 직접 호출 대비 비교 측정한다.
6. 결과가 유의미하면, ai-info-radar 파이프라인 중 "기사 관련도 점수 매기기" 같은 단순 판정 스텝 하나를 골라 Jev 서버 호출로 교체하는 실험 브랜치를 만든다.
7. 비용/속도 개선폭을 기존 launchd 배치 로그와 비교해 정량 확인 후, 개선 폭이 크면 나머지 파이프라인 단계로 점진 확장한다.

## 예상 공수
- PoC(빌드+간단 테스트): 3~5시간, 난이도 중~상 (Rust/신생 프로토콜 문서 부족으로 시행착오 예상)
- ai-info-radar 실제 통합: 추가 4~8시간, 난이도 상 (기존 채점 로직과의 인터페이스 설계 필요)
- 총 1~2일 분산 작업 권장, 바로 상용화보다는 사이드 실험으로 접근 추천

## 리스크/유의점
- 프로젝트 자체가 검증되지 않은 초기 단계라 유지보수 중단·breaking change 위험이 높음.
- TypeSafe AI가 유료 서비스일 경우, "비용 절감"이라는 도입 목적과 상충할 수 있으니 요금제부터 확인 필요.
- Jev는 자유 텍스트 생성이 아닌 정형 판정에 특화되어 있어, ai-info-radar의 브리핑 작성처럼 서술형 작업에는 적용 불가 — 적용 범위를 분류/라우팅류로 한정해야 함.
- Rust 빌드 환경 관리 부담이 있으므로, ROI가 확인되기 전까지 프로덕션(launchd 자동 배포)에 바로 반영하지 말고 별도 실험 스크립트로 격리해서 테스트할 것.
